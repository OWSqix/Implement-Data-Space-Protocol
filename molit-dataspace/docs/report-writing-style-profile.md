## 1. 분석 목적과 적용 범위

이 문서는 기획보고서의 형식적 특징을 재현 가능한 작성 규칙으로 바꾼다. 대상은 이 저장소에서 새로 작성하거나 개정하는 연구, 설계, 계획, 검토 문서다.

- **(채택 대상)** 위계가 분명한 개조식 구조, 명사구 제목, 결론 우선 배열, 비인칭 문어체, 첫 등장 용어 정의
- **(제외 대상)** 홍보성 수사, 근거 없는 효과, 주체 없는 계획, 절대적 기술 단정, 용어 표기 불일치
- **(우선순위)** 사실 정확성, 근거 추적성, 기술 경계, 문체 순으로 적용
- **(판정 원칙)** 원문의 문체와 원문의 기술 주장을 분리하며, 문체를 맞추기 위해 잘못된 주장을 유지하지 않음

### 1.1 분석 단위

보고서 표기 p.1~214의 본문과 p.215~307의 별첨·RFP·과제카드는 목록 표지가 달라 별도 집계했다. PDF의 줄바꿈을 결합한 뒤 제목 표지, 목록 표지, 종결형, 괄호 라벨, 한영 병기와 용어 변형을 계수했다.

정량값은 문체 지문을 설명하기 위한 근사치다. PDF 표, 그림, 각주와 자동 줄바꿈 때문에 원고 파일을 직접 계수한 값과 다를 수 있다. 수치 자체를 품질 점수로 사용하지 않는다.

### 1.2 적용 단위

하네스는 Markdown 파일의 제목, 목록과 일반 문장을 검사한다. 다음 영역은 문체 규칙에서 제외한다.

- fenced code와 들여쓴 code
- Markdown 표와 blockquote
- 하이퍼텍스트 마크업 언어(HyperText Markup Language, HTML) comment
- `금지할 설명`, `나쁜 예`, `교체 전`, `원문 인용` 절의 예시
- 별도 문체가 필요한 대외 문의문 중 설정에 등록된 파일

### 2.3 문장 종결

본문 `□`, `○`, `-` 2,010개 블록에서는 `~다` 종결이 검출되지 않았다. 행위명사 종결은 약 30.7%, `있음`, `없음`, `함`, `임`, `됨`, `필요` 종결은 약 18.4%다. 목록 시작 행의 94.6%는 문장부호 없이 끝난다. 근거: 분석 대상 PDF p.13~319의 추출문 계수

이 수치는 모든 문장을 명사형으로 바꾸라는 지시가 아니다. 같은 위계에서 문법형을 맞추고, 상태와 행위를 짧게 구분하는 방식만 채택한다.

| 기능 | 권장 종결 | 사용 조건 |
| --- | --- | --- |
| 현황 | `~운영 중`, `~확인됨`, `~있음` | 관찰 주체와 근거가 앞 절에 있음 |
| 판단 | `~로 판단`, `~에 해당`, `~필요` | 판정 기준을 함께 제시 |
| 결정 | `~로 채택`, `~에서 제외` | 결정권자와 상태를 기록 |
| 계획 | `~수립`, `~개발`, `~적용`, `~검증` | 담당, 산출물과 완료조건을 함께 제시 |
| 의무 | `~해야 함`, `~하여야 함` | 검증 방법과 실패 기준이 있음 |
| 설명 | `~다` | 인과관계나 기술 경계를 완전한 문장으로 설명 |

### 2.4 괄호형 선행 라벨

`(법적 제약)`, `(중점1)`, `(국가데이터인프라)`와 같은 선행 라벨은 368행, 97쪽에서 확인됐다. 라벨은 문장의 범주를 먼저 고정한다.

- **(허용)** 판단, 근거, 범위, 예외, 담당, 산출물, 검증처럼 읽는 목적을 밝히는 짧은 라벨
- **(제한)** 한 항목에 선행 라벨 하나만 사용
- **(금지)** 라벨 안의 중첩 괄호, 본문을 대신하는 긴 라벨, 의미가 없는 `핵심` 또는 `중요`

### 2.5 한영 용어 병기

한글 뒤에 영문을 괄호로 병기한 행은 373행, 132쪽에서 확인됐다. 영문 풀네임과 약어를 함께 적은 행은 85행, 57쪽이다.

- **(첫 등장)** `국문 용어(Official English Term, ACRONYM)` 형식으로 정의
- **(이후 사용)** 문맥이 고정되면 약어 또는 대표 표기 사용
- **(공식 표기)** 표준명, 제품명, protocol object와 API field는 원문 표기 유지
- **(번역 제한)** 표준의 규범 용어를 임의의 유사어로 바꾸지 않음

### 2.6 표, 그림과 출처

추출본에는 `<그림>` 86개와 `<표>` 83개가 있다. 명시적인 `출처:` 행은 19개, 번호 각주 시작 행은 40개다.

- **(캡션)** 보고서 원형은 `<표 장-번호> 제목`, `<그림 장-번호> 제목` 사용
- **(표 머리말)** `구분`, `주요 내용`, `현황`, `목표 수준`, `검증 방안`처럼 비교 기능을 나타내는 명사 사용
- **(외부 자료)** 발행기관, 자료명, 발행일, 기준일, URL 또는 source ID 기록
- **(재구성 자료)** `재구성` 여부와 원자료 위치 기록
- **(기술 표준)** 표준명, version, 문서 상태, 발행일 또는 확인일 기록

원문의 출처 표기는 충분하지 않다. 이 저장소에서는 출처와 기준일을 추가해 적용한다.

## 3. Markdown 적용 구조

PDF의 특수문자를 그대로 복제하지 않는다. Markdown의 제목과 중첩 목록으로 같은 역할을 표현한다.

| 보고서 역할 | Markdown 표현 | 작성 내용 |
| --- | --- | --- |
| 장 | `## 1. 제목` | 문서의 큰 판단 영역 |
| 절 | `### 1.1 제목` | 같은 장의 분석 단위 |
| 항 | `#### 1.1.1 제목` | 세부 절이 실제로 필요할 때만 사용 |
| `□` | 최상위 bullet | 판단, 방향 또는 상태 |
| `○` | 한 단계 중첩 bullet | 근거, 이유 또는 하위 판단 |
| `-` | 두 단계 중첩 bullet | 동작, 조건, 예시 또는 산출물 |
| `*` | 별도 주석 또는 note | 예외, 정의 또는 제한 |

### 3.1 기본 골격

문서에는 H1 하나를 둔다. H2는 `1.`부터 연속된 십진 번호를 사용한다. 첫 30행 안에서 목적, 범위, 질문, 판정 또는 기준을 밝힌다.

```markdown
# 문서 제목

작성일: YYYY-MM-DD  
상태: Draft

## 1. 목적과 범위

- **(목적)** 문서가 내릴 결정 또는 답할 질문
- **(범위)** 포함 대상과 제외 대상

## 2. 판정

### 2.1 핵심 판정

- **(판정)** 결론
  - **(근거)** 결론을 지지하는 사실과 source ID
  - **(조건)** 결론이 성립하는 범위와 실패 조건
```

### 3.2 정보 배열

한 논점은 다음 순서로 작성한다.

1. 판정 또는 현황
2. 판정 기준
3. 확인 근거
4. 구현 동작 또는 수정안
5. 예외와 미확인 사항
6. 검증 방법과 산출물

모든 절에 여섯 항목을 기계적으로 채우지 않는다. 해당 내용이 있을 때만 사용하되 결론보다 배경 설명을 먼저 길게 두지 않는다.

## 4. 문장 작성 규칙

### 4.1 제목

- 명사구 사용
- 질문문과 감탄문 제외
- `개요`, `기타`, `고찰`처럼 범위를 알 수 없는 제목 지양
- 제목에서 결론을 과장하지 않고 본문 첫 항목에서 판정 제시

### 4.2 한 항목의 판단 수

한 bullet에는 하나의 판단만 둔다. 근거, 조건과 예외가 길어지면 하위 bullet로 분리한다.

쉼표가 다섯 번 이상, `및`이 세 번 이상, 괄호가 세 쌍 이상 나타나는 행은 분리 여부를 검토한다. 자동 검사는 정보 신호만 제공하며 문법적 오류를 확정하지 않는다.

### 4.3 주체와 동작

비인칭 문체는 작성자와 독자를 지우는 규칙이다. 시스템 동작과 의무의 주체까지 지우는 규칙이 아니다.

```text
나쁨: 계약 종료 시 접근권한 회수 필요
교정: Lifecycle Adapter는 계약 종료 event를 받으면 platform token과 subscription을 삭제해야 함
검증: 종료된 Agreement ID로 원천 API를 호출했을 때 403을 반환하고 삭제 event를 audit log에 기록
```

### 4.4 계획 항목

`지원`, `연계`, `관리`, `고도화`, `활성화`, `추진`, `구축`만으로 계획을 끝내지 않는다. 다음 필드를 문장 또는 표에서 확인할 수 있어야 한다.

- **(담당)** 작업 책임을 지는 기관, 팀 또는 component
- **(입력)** 필요한 source record, 계약, schema 또는 승인 문서
- **(산출물)** API, mapping, manifest, report, decision record 또는 운영 절차
- **(기한)** 날짜, 단계 또는 선행조건
- **(완료조건)** 시험 결과, 상태 전이, 오류 건수 또는 승인 기록

### 4.5 직접 호명과 존대

`저`, `제가`, `저희`, `여러분`, `당신`, `독자 여러분`을 사용하지 않는다. `합니다`, `됩니다`, `있습니다`, `해요`, `까요`, `십시오` 종결도 일반 보고서 본문에서 사용하지 않는다.

대외 문의문, 설문 안내와 사용자 화면 문구는 기능상 별도 문체가 필요하다. 해당 파일은 configuration override로 명시하며 일반 문서에 예외를 확장하지 않는다.

## 5. 사실, 판단과 근거

### 5.1 상태 표지

| 상태 | 의미 | 필요한 기록 |
| --- | --- | --- |
| `Verified` | 1차 출처 또는 재현 가능한 관찰에서 직접 확인 | source ID, URL, page, 관찰일 또는 시험 기록 |
| `Inferred` | 확인 사실에서 도출한 해석 | 전제, 추론 과정과 확인 담당 |
| `Unverified` | 필요한 자료나 시험을 확보하지 못함 | 확인 대상, 담당과 다음 조치 |
| `Decision` | 프로젝트가 선택한 방안 | 결정권자, 상태와 ADR |

상태 표지만 붙여 근거를 대신하지 않는다. `Verified`에는 무엇을 어디에서 확인했는지 기록한다.

### 5.2 수치와 최신성

연도, 비율, 시장규모, 기술격차, `최초`, `최신`, 표준화 상태를 주장할 때 다음 정보를 붙인다.

- 발행기관과 문서명
- 기준일과 예측기간
- 분자, 분모 또는 산정 방법
- URL, source ID와 page
- 문서 상태가 바뀔 수 있으면 재확인 시점

### 5.3 절대 표현

`완벽`, `100%`, `즉시`, `항상`, `모든`, `비유출`, `호환성을 보장`은 범위와 시험 근거 없이 사용하지 않는다. 필요한 경우 다음 정보를 같은 항목 또는 인접한 근거 항목에 둔다.

- 보장 대상과 제외 범위
- 정상 조건과 실패 조건
- 측정 방법과 표본
- 시험 환경과 version
- 통과 기준과 evidence ID
- 잔여위험과 책임 주체

## 6. 용어와 표준명

### 6.1 대표 표기

| 비대표 표기 | 대표 표기 |
| --- | --- |
| `데이터스페이스` | `데이터 스페이스` |
| `Data Space Protocol` | `Dataspace Protocol` |
| `GAIA-X`, `Gaia X` | `Gaia-X` |
| `As-Is` | `AS-IS` |
| `To-Be`, `To-be` | `TO-BE` |
| `유즈 케이스` | `유즈케이스` |

대표 표기는 `report-style.config.json`에서 관리한다. 용어를 추가할 때는 비대표 표기와 교체할 대표 표기를 함께 등록한다.

### 6.2 표준 범위

표준명 뒤에는 필요한 경우 version과 문서 상태를 적는다. 표준의 범위, Connector 제품의 구현과 프로젝트 결정을 한 문장에 섞지 않는다.

- **(규범)** 표준이 요구하거나 허용하는 동작
- **(구현)** 특정 Connector 또는 Bridge가 제공하는 기능
- **(결정)** 이 프로젝트가 채택하거나 제외한 방안
- **(검증)** 실제 환경에서 확인할 시험과 acceptance criterion

## 7. 표와 그림

### 7.1 표 사용 조건

표는 역할, 상태, 선택지, version, 입력·출력처럼 공통 비교축이 있을 때 사용한다. 한 열짜리 목록이나 긴 문장을 셀에 나눠 넣기 위한 표는 사용하지 않는다.

### 7.2 캡션과 근거

재사용되는 표와 그림에는 문서 안에서 고유한 제목을 붙인다. 외부 자료를 재구성한 경우 원자료와 재구성 범위를 기록한다.

```text
표 4-1. Connector와 기존 플랫폼의 책임 경계
출처: SRC-TECH-001, 확인일 2026-07-11, 작성자가 역할 기준으로 재구성
```

화면 캡처에는 계정명, token, cookie, API key와 개인정보가 없어야 한다. 원본 증거와 공개 문서용 이미지를 분리한다.

## 8. AI Slop 배제 규칙

### 8.1 진행 설명

다음 표현은 내용을 시작하지 않고 작성 행위를 설명하므로 삭제한다.

- `오늘은 ~를 알아본다`
- `이번 글에서는 ~를 살펴본다`
- `함께 구현해보자`
- `여정을 시작한다`
- `이제 본격적으로 들어가 보자`

첫 문장은 목적, 판정, 범위 또는 관찰 사실로 시작한다.

### 8.2 상투적 대비와 전환

다음 구문은 구체적 차이를 쓰지 못하면 삭제한다.

- `핵심은`
- `궁극적으로`
- `단순히 A가 아니라 B`
- `A를 넘어 B`
- `새로운 패러다임`
- `선순환 생태계`
- `이를 통해 활성화`
- `새로운 가치를 창출`
- `토대를 마련`

### 8.3 홍보성 수사

`혁신적`, `강력한`, `원활한`, `효율적인`, `최적의`, `미래지향적`, `획기적`, `폭발적`, `비약적`, `막대한`을 평가 기준 없이 사용하지 않는다.

```text
나쁨: 안정적이고 효율적인 연계 환경 구축
교정: 동일 idempotency key의 활성 subscription을 하나만 유지하고, 종료 뒤 접근시험에서 403을 반환
```

### 8.4 반복과 형식 채우기

- 같은 결론을 서론, 본문, 표와 맺음말에서 반복하지 않음
- 항목 수를 맞추기 위한 동의어 bullet을 만들지 않음
- 새 정보가 없는 절별 요약과 별도 맺음말을 만들지 않음
- 비교축이 없는 표를 만들지 않음
- 근거가 없는 일반론으로 문서 분량을 늘리지 않음

## 9. 기술 정확성 안전장치

보고서 문체를 따르더라도 다음 범위 오류는 사용하지 않는다.

| 대상 문장 또는 표현 | 판정 | 교정 방향 |
| --- | --- | --- |
| `DSP가 실제 데이터를 전송한다` | DSP와 payload transport의 범위를 혼동 | DSP는 Catalog, Contract Negotiation과 Transfer Process를 조정하며 실제 전송 profile은 별도 명시 |
| `DCP는 DSP의 필수 구성요소다` | 별도 규격을 필수 stack으로 고정 | identity 요구와 상호운용 대상을 확인한 뒤 DCP 채택 여부를 결정 |
| `TCK 인증` | 적합성 시험과 인증을 혼동 | 적용 TCK release, 통과 case와 제외 범위를 기록 |
| `ODRL이 사후 사용을 보장한다` | 정책 표현과 집행을 혼동 | ODRL rule을 PDP, PEP, Data Plane, 감사와 계약상 통제에 mapping |
| `DCAT-AP가 분산 Catalog를 구현한다` | metadata profile과 federation 동작을 혼동 | 수집, cache, 접근제어와 동기화는 별도 Catalog architecture로 정의 |
| `JSON-LD가 용어를 자동 mapping한다` | serialization과 semantic alignment를 혼동 | mapping rule, version, 단위, CRS, provenance와 검증 결과 관리 |
| `C2D이면 민감정보 교환이 가능하다` | 처리 방식과 법적 근거를 혼동 | 데이터 등급, 처리 근거, 실행 통제와 결과 반출 심사를 별도 승인 |

이 표는 자동 검사의 `TRM101`에 반영된 최소 금지 패턴이다. 정규식에 걸리지 않았다고 기술적으로 정확한 것은 아니다.

## 10. 교정 예시

### 10.1 대화형 도입

```text
대상 문장: 오늘은 국토교통 데이터 플랫폼을 데이터 스페이스와 연결하는 방법을 알아보고 구현할 예정이다.
수정 문장: 이 문서는 국토교통 데이터 플랫폼의 Dataset을 DSP Offering으로 게시하고 기존 접근 기능을 Agreement 수명주기에 연결하기 위한 책임 경계와 검증 항목을 정의한다.
```

### 10.2 주체 없는 계획

```text
대상 문장: 메타데이터 연계체계 구축 및 고도화 추진
수정 문장: Catalog Adapter 담당팀은 source record의 delta와 tombstone을 수집해 DCAT Dataset을 갱신하고, 매일 reconciliation report에서 누락·중복·삭제 실패 건수를 확인해야 함
```

### 10.3 근거 없는 보장

```text
대상 문장: 표준 Connector를 적용해 글로벌 상호운용성을 100% 보장한다.
수정 문장: 고정한 DSP version과 TCK release의 적용 가능한 Provider·Consumer test case를 통과하고, 별도 Connector 구현체 두 종 사이에서 Catalog·Agreement·Transfer·termination 시나리오를 재현한다. 제외 case와 실제 payload profile은 별도 기록한다.
```

### 10.4 AS-IS와 TO-BE

```text
나쁨: AS-IS는 폐쇄형 플랫폼이고 TO-BE는 혁신적인 데이터 스페이스다.
교정: AS-IS에는 현재 관찰, source와 운영 제약을 기록한다. TO-BE에는 목표 동작, 전환 조건, 담당과 검증 기준을 기록한다.
```

## 11. 자동 규칙 대응표

| Rule ID | 기본 severity | 검사 대상 |
| --- | --- | --- |
| `STR001` | error | H1 개수와 heading level 건너뛰기 |
| `STR002` | error | H2 십진 번호와 순서 |
| `STR003` | warning | H3 이하의 decimal, finding 또는 한글 번호 scheme |
| `STR004` | warning | 첫 30행의 목적·범위·질문·판정·개요·기준 |
| `REG101` | error | 대화형 진행 설명 |
| `REG102` | error | 존대형과 대화형 종결 |
| `REG103` | warning | 목록의 개조식·평서형 종결과 문장부호 |
| `REG104` | error | 작성자 또는 독자 직접 호명 |
| `REG105` | warning | 상투적 강조와 전환 |
| `REG106` | warning | 근거 없는 홍보성 수사 |
| `REG107` | warning | 180자 초과 행 |
| `REG108` | info | 과도한 쉼표, 괄호와 `및` 병렬 |
| `REG109` | warning | 같은 문서 안의 긴 문장 중복 |
| `PRE101` | warning | 동작과 완료조건이 없는 행위명사 계획 |
| `PRE102` | error | 근거 없는 절대적 기술 단정 |
| `PRE103` | warning | 검증 기준이 없는 의무 표현 |
| `PRE104` | warning | 출처가 없는 수치·최신성·표준 상태 주장 |
| `TRM101` | error | 판정된 DSP·DCP·TCK·ODRL·DCAT 범위 오류 |
| `TRM102` | info | 첫 정의가 없는 약어 |
| `TRM103` | warning | 대표 표기 불일치 |

기본 gate는 `error`와 `warning`에서 실패한다. `error`는 확정 위반, `warning`은 사람의 판정이 필요한 항목이다. `info`는 자동 판정의 신뢰도가 낮은 점검 목록이며 gate를 실패시키지 않는다.

## 12. 작성과 검토 절차

1. `tools/report-style/templates/report-document.md`에서 문서 골격을 가져옴
2. 첫 절에 목적, 범위, 포함 대상과 제외 대상 기록
3. 외부 사실에 source ID, page, URL과 기준일 연결
4. 사실, 추론, 미확인과 프로젝트 결정을 분리
5. `npm run docs:style`로 error와 warning 검사
6. diagnostic을 문장별로 검토하고 필요한 예외에만 사유가 있는 한 줄 suppression 사용
7. `--fail-on none` 결과에서 info 항목의 약어와 병렬 나열을 검토
8. 기술 검토자가 표준 범위, source와 acceptance criterion을 별도 확인

## 13. 예외와 한계

### 13.1 허용 예외

한 줄 예외는 규칙 ID와 사유를 함께 기록한다.

```markdown
<!-- report-style-disable-next-line PRE102: 발간 보고서 제목을 원문 그대로 인용 -->
```

영역 전체를 끄는 지시와 legacy baseline은 두지 않는다. 예외가 반복되면 파일 단위 override를 configuration에 추가하고 기능적 이유를 문서화한다.

### 13.2 자동 검사의 한계

- 한국어 주체, 수식 범위와 인과관계의 타당성을 판정하지 못함
- 출처가 실제로 주장을 지지하는지 확인하지 못함
- 표 안의 문체와 복잡한 CommonMark 구조를 검사하지 않음
- 의미가 다른 문장을 같은 표현으로 정규화하거나 의미가 같은 문장을 다른 표현으로 놓칠 수 있음
- 규칙 위반이 없더라도 기술적 정확성과 보고서 승인 상태를 보장하지 않음

자동 수정은 제공하지 않는다. 문체 교체 과정에서 책임 주체, 규범 강도와 기술 의미가 바뀔 수 있기 때문이다.
