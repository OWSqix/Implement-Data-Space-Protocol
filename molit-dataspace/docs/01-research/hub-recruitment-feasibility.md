# 기존 플랫폼 섭외 가능성 조사

작성일: 2026-08-03  
작성 기준: 외부자료 확인 2026-08-02·저장소 문서 상태 2026-08-03  
상태: Draft  
작성자: 연구 담당  
관련 결정: [ADR-0003](../adr/0003-existing-platform-integration-topology.md) — 기존 플랫폼 비대체 원칙만 승계, 섭외 순서는 연구 권고

## 1. 목적과 범위

- **(목적)** 현행 역량이 부족한 7개 허브에 기능과 권리를 추가로 확보할 수 있는지 판정
- **(질문)** 현재 연계할 수 없다는 판정과 섭외 뒤 연계할 수 있다는 판단을 어떤 조건에서 구분하는가
- **(포함 범위)** 소관·지배구조, 발주·부처 협의 경로, 원천 권리, 리드타임, 해외 선례, 실행 순서와 허브별 협상 요인
- **(제외 범위)** 6차 허브 역량 조사(`M6`)의 7개 축 재판정, 커넥터(Connector) 제품 선택, 개별 계약·조례의 최종 법률의견, 확정 예산과 사업기간
- **(판정 기준)** 정책방향을 말할 수 있는지가 아니라 요구된 기능과 권리를 실제 운영에 반영할 수 있는지로 난도 판정

외부 URL의 확인일은 2026-08-02다. `M6`는 현행 역량을 판정했고, 7차 섭외 조사(`M7`)는 섭외 가능성만 분석했다. 근거: `SRC-INT-001`, `SRC-INT-002`

이 문서는 두 조사 원문의 수치·범위·한계를 유지한다.

### 1.1 읽기 주의 — 조사 원문 용어와 저장소 아키텍처의 관계

- **(Verified — 문서 성격)** 이 문서는 **조사 원문을 전사한 기록**이며 설계 결정문이 아니다.
- **(Verified — 용어 출처)** 본문의 **"게이트웨이"는 조사자의 용어**다.
- **(Decision — 적용 기준)** 저장소의 아키텍처 취급은 [ADR-0002](../adr/0002-data-stays-at-source.md)와 [ADR-0008](../adr/0008-provider-default-and-existing-system-participation.md)을 따른다.
  - **(경계)** **데이터 스페이스는 payload를 보관하지도 중계하지도 않는다.** 참가자는 제공 가능한 상태를 만들고 수요자는 계약을 맺고 원천에서 당겨간다.
- **(Decision — E-19)** 기존 정산 시스템(회계처리·버스경영관리시스템)은 **Consumer로 온보딩**한다. 계약을 맺고 운수사 원천에서 당겨온다
- **(해석 경계)** 본문에 중앙 수신·중계로 읽히는 서술이 있다면 그것은 조사 원문의 표현이며 채택된 설계가 아니다.

## 2. 현재 판정

### 2.1 한 줄 판정

- **(Inferred)** **한 줄 판정 — 선별 데이터에 한해 조건부 가능하다. 국토부 소관 시스템의 기능은 발주로 만들 수 있고 타부처 시스템도 협의할 수 있지만, 허브가 보유하지 않은 원천 재제공권은 발주나 지시로 만들 수 없다.** 근거: `SRC-INT-002`
- **(Verified)** 승계 사실 — `M6` 산출물인 [기존 허브의 데이터 스페이스 연계 역량 조사](hub-capability-assessment.md)는 공개 문서 기준으로 7개 허브 전부를 현 상태의 Mobilithek형 연계 불가로 판정했다. 근거: `SRC-INT-001`, `SRC-INT-006`
- **(Decision)** **초기 실증을 허브 섭외에 종속시키는 것은 권고하지 않는다.** 직접 경로를 먼저 완주하고 권리가 확인된 데이터만 허브에 연결한다. 근거: `SRC-INT-002`

## 3. 승계 범위와 섭외 난도

### 3.1 `M6` 판정의 승계

- **(Verified)** `M6`는 데이터 보유 형태, 구독·엔타이틀먼트, 회수, 수신확인·감사, 인증, 원천 권리와 이용 조건의 7개 축을 조사했다. 근거: `SRC-INT-001`
- **(Verified)** 공개 문서로 구독·회수·감사 세 축을 함께 확인한 허브는 0곳이고, 확정 가능한 `brokered` 경로도 0개다. 근거: `SRC-INT-001`
- **(제한)** `M6`의 `unknown`은 `index-only`가 아니다. 공개 문서만으로 전달·책임 구조를 판정할 수 없다는 뜻이다. 근거: `SRC-INT-001`
- **(제한)** 이 문서는 같은 배치의 `M6` 산출물을 승계하며 7개 축을 다시 판정하지 않는다.
- **(정정)** `M7`은 ADR-0003과 통합채널 역량 프로파일을 7개 허브 판정의 승계 근거로 잘못 지목했다. 실제 상세 근거는 `M6`다. 추적: `OPEN-HRF-01`

### 3.2 난도 등급 기준

| 등급 | 실제 운영 반영 기준 | 허브 수 |
| --- | --- | ---: |
| 지시 가능 | 별도 발주·타부처 합의·원천 권리 추가 없이 지시만으로 기능과 권리를 반영 | 0곳 |
| 발주 필요 | 국토부가 정책·위탁범위를 정할 수 있으나 코드·계약·보안 변경에 과업변경 또는 신규 발주가 필요 | 4곳 |
| 협의 필요 | 타부처·한국지능정보사회진흥원(National Information Society Agency, NIA)의 사업·운영 결정이 필요 | 2곳 |
| 구조적 곤란 | 운영자 한 곳과의 합의로 다수 원천 권리자를 대표할 수 없는 구조 | 1곳 |

`M7`은 이 기준으로 0곳·4곳·2곳·1곳을 판정했다. 상태는 `Inferred`다. 근거: `SRC-INT-002`

- **(Verified)** 공공데이터전략위원회에는 국토교통부장관이 당연직으로 참여한다. 근거: `SRC-HUB-010`

## 4. 원천 권리와 조건부 가능 범위

### 4.1 발주로 만들 수 없는 권리

| 법적 경계 | 확인 내용 | 운영상 의미 | 상태·근거 |

- **(Verified)** 교통카드 선례는 가상 카드번호, 폐쇄공간, 사전승인과 결과 반출심사를 사용하고 원자료를 외부로 내보내지 않았다. 근거: `SRC-RGT-004`, `SRC-RGT-005`; 인용 page: `OPEN-HRF-03`
- **(Inferred)** 가장 근거가 강한 구조는 허브를 권리자가 아닌 전달자로 두고 원천기관을 Provider로 유지하는 방식이다. 근거: `SRC-INT-002`, `SRC-RGT-002`

### 4.3 초기 유즈케이스의 재판정 조건

- **(Verified)** 성과지표(Key Performance Indicator, KPI)를 다룬 [초기 유즈케이스·KPI](../03-plan/initial-usecases-and-kpi.md)는 2026-08-01 작성된 `Draft`다. 근거: `SRC-INT-003`
- **(Verified)** 현 경계는 정산 명세·대사 결과·공통 감사 ID이며 원시 교통카드, 개인·가명 식별값과 결제수단 원문을 제외한다. 근거: `SRC-INT-003`
- **(Decision)** 정산 원자료에 교통카드·개인·결제 데이터가 다시 포함되면 권리·샌드박스 경로를 재판정한다. 근거: `SRC-INT-002`, `SRC-INT-003`, `SRC-RGT-001`

## 7. 실행 순서

### 7.1 여섯 단계

실증 담당팀은 다음 순서를 `Decision`으로 사용한다. 각 단계의 범위는 선행 단계에서 확인한 권리와 데이터 분류를 넘지 않는다. 근거: `SRC-INT-002`, `SRC-INT-003`, `SRC-INT-004`

1. **원천 권리 확정**
   - 파일럿 지자체 조례, 준공영제 협약, 정산 위수탁계약과 운수사 권리를 확인하고 Provider를 운수사 또는 명시적 수임기관으로 기록
2. **표준 참여계약·데이터 분류**
   - 목적·수신자·항목·기간·재전송·회수·감사·책임을 부속합의서에 기록하고 미동의·민감 항목을 제외·집계·폐쇄환경 중 하나로 분류
3. **허브 없이 직접 게이트웨이 1건 완주**
   - 운수사 1곳에서 [플랫폼 인터페이스 계약](../02-architecture/platform-interface-contract.md)의 생성·정지·재개·삭제·감사 흐름을 연결하고 같은 계약 ID의 증거를 보존
4. **권리 확인 데이터만 첫 허브 1곳에 연결**
   - 대중교통 보조데이터에는 국가대중교통정보센터, 연합검색에는 통합채널 중 실제 유즈케이스에 필요한 한 곳을 선택
5. **패턴 확정 후 타부처 협의**
   - 동작한 계약·API·보안 결과와 비용·책임 범위를 가지고 행안부·과기정통부·NIA 조정 경로에 공동사업 안건 제시
6. **국가교통정보센터·K-MaaS·오픈마켓 확장**
   - 실제 유즈케이스가 생긴 순서로 추가하고 오픈마켓은 운영자 일괄협상이 아닌 판매자별 Provider 온보딩으로 처리

### 8.2 공통 레버리지 묶음

- **(Decision)** 가장 강한 레버리지는 “국토부 사업이니 따르라”가 아니라 다음 여섯 조건의 묶음이다. 근거: `SRC-INT-002`
  - 개발·운영비의 전액 또는 공동 부담
  - 원천기관 책임을 허브에 전가하지 않는 전달자 구조
  - 권리 확인 데이터만 허용하는 허용목록
  - 장애·보안·감사 책임의 명시적 분담
  - 기존 개별 API·민원 대응을 줄이는 업무 절감
  - 참여기관별 탈퇴·회수 경로 보장
